# wb-service

## Путь карточки

1. `cardimport` хранит незавершённую сессию, файлы и разобранные карточки в памяти. При `Finalize` он одной транзакцией сохраняет заголовок в `wb.card_batches` и карточки в `wb.card_batch_items`. Перезапуск до завершения `Finalize` требует повторной загрузки файлов.
2. `transfer` сам ищет запечатанные пачки без записи в `wb.transfers`. Каждый проход поиска начинается с начала; курсор используется только внутри прохода. Ошибка одной пачки не мешает обработке следующих, а пачка без transfer попадёт в следующий проход.
3. `Start` выбирает кабинеты и создаёт transfer в фазе `initializing`. `Initialize` копирует группы и карточки в таблицы transfer, создаёт их связи с кабинетами, переводит transfer в `active` и удаляет исходные строки `card_batch_items` в **одной транзакции**. После этого подготовка и публикация работают с копией transfer.
4. `cardprepare` готовит данные карточек для каждого кабинета. `cardpublication` планирует и выполняет отправку в WB, затем сохраняет результаты. Transfer завершает работу после обработки всех групп и кабинетов.

У transfer три фазы: `initializing`, `active`, `finished`. Во время `active` точный прогресс хранится в группах, карточках и действиях публикации. Итоги: `succeeded`, `partial`, `rejected`, `unresolved`, `failed`.

## Группы и повторные запуски

При `Finalize` каждая уникальная пара «исходный файл, название группы» получает номер от 1 в порядке первого появления. Карточки одной группы в одном файле имеют одинаковый номер; совпадающие названия в разных файлах получают разные номера. Пустая группа отклоняется при импорте.

После перезапуска transfer возобновляет записи в фазе `initializing` и повторно находит запечатанные пачки без transfer. `Initialize` сообщает о прогрессе только тогда, когда действительно перевёл запись в `active`, поэтому параллельные вызовы не создают повторное уведомление.

Для чистой инициализации используется базовая схема из `migration/`. Проверка: `go test ./...`; интеграционные тесты на отдельной PostgreSQL: `make postgres-integration-test-local`.

## PostgreSQL и токены кабинетов

`POSTGRES_TIMEOUT` ограничивает каждый SQL-запрос на стороне PostgreSQL через `statement_timeout`. Репозитории также используют его для контекста отдельной операции. Общий срок составной транзакции задаётся контекстом её вызывающего кода.

Токены WB сохраняются в `wb.api_cabinets.token` в исходном виде. Доступ к этой таблице и резервным копиям БД должен быть ограничен; шифрования токенов на уровне приложения сейчас нет.
