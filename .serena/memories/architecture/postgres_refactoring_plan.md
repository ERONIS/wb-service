# План рефакторинга PostgreSQL и репозиториев

## Назначение и границы

- Статус: план с историческими отметками выполненных фаз; текущие решения определяются состоянием кода и указаниями пользователя.
- Текущий сценарий развёртывания: пользователь заново инициализирует БД. Upgrade прежней схемы подготовки и перенос её данных не входят в работу. Для PostgreSQL-изменений проверять полное применение миграций с пустой БД и соответствие итоговой схемы текущему коду. Исторические требования upgrade ниже не являются текущим критерием для этой переинициализации.
- Цель: упростить сопровождение репозиториев, сделать транзакционные границы проверяемыми, добавить диагностику и устранить подтверждённые ограничения производительности.
- Базовый подход: сохранить явную передачу транзакции, менять модули небольшими независимыми шагами, проверять поведение до и после каждого существенного изменения.
- Выбранный внешний ориентир для PostgreSQL-архитектуры — Hatchet (`github.com/hatchet-dev/hatchet`, `pkg/repository`): явные pgx-транзакции, вариант операции с переданным tx для композиции, выборочные блокировки и SQL-first репозитории. Заимствовать паттерны по потребности; действующие UoW, доменные инварианты и правила WB-мутаций остаются исходным контрактом.
- Неизменяемые требования: атомарность артефактов и проекций, идемпотентность, конечные автоматы transfer/publication, авторизация кабинетов, канонические хеши, точные байты публикационных payload, CHECK/FK/UNIQUE и триггеры иммутабельности.
- Количество строк — вспомогательная метрика. Заранее обещанное сокращение на 35–40% и ускорение исключены: эффект подтверждается пилотом и измерениями.
- Рефакторинг PostgreSQL не меняет правила повторных WB-мутаций и восстановления после неопределённого результата внешнего запроса.

## Исходные факты

- Крупные файлы cardpublication/product.go, media.go, cardimport/batch.go и transfer/live_authorization.go объединяют несколько групп операций; их можно разделить внутри существующих пакетов.
- UoW имеет контракт WithinTransaction(ctx, func(ctx, DBTX) error). Критические методы transfer/publication получают DBTX явно. Репозиторий transfer хранит неиспользуемую зависимость uow.
- wbcabinet.UpsertVerified выполняет короткую атомарную операцию хранения. Service.Add проверяет WB до неё и активирует runtime после успешного commit.
- OperationContext использует настраиваемый Config.Timeout только там, где его вызывают. Он не устанавливает общий фиксированный таймаут на все UoW и CopyFrom.
- pgxpool.ParseConfig уже используется. Проблема подключения — конструирование URI через fmt.Sprintf без экранирования компонентов.
- Очередь подготовки использует keyset по (source_group_id, target_id). Помимо partial index на transfer_id существует UNIQUE (transfer_id, source_group_id, target_id).
- ApplyPreparationResult блокирует строку transfers до group target. Запись результатов разных групп одного transfer сериализуется; влияние на throughput требует измерений.
- Маппинг PostgreSQL-ошибок уже присутствует в wbcabinet и users; дальнейшая унификация должна сохранять доменную семантику.

## Целевая архитектура

### 1. Явные транзакции и короткие границы UoW

- Сохранить WithinTransaction(ctx, fn) и явный tx DBTX у операций, которым нужна общая транзакция. В составных сценариях использовать существующие ApplyTx/аналогичные методы внутри одной внешней UoW.
- Не внедрять транзакции через context и r.db(ctx) с автоматическим fallback на pool. Ошибка передачи контекста не должна превращать атомарную команду в несколько autocommit-записей.
- DBTX — структурный интерфейс, который может реализовывать и pool; сам тип не доказывает наличие транзакции. Транзакционный исполнитель поступает из callback UoW, его происхождение и общий rollback проверяются контрактными тестами.
- Чтения, участвующие в read-modify-write и блокировках, должны выполняться через тот же tx. Независимые чтения могут использовать pool.
- Владельцем commit/rollback является внешняя UoW. Внутренние ApplyTx не открывают новую транзакцию и не завершают переданную.
- Не вызывать самостоятельный WithinTransaction из уже выполняющегося callback: это может открыть независимую транзакцию. Вложенный сценарий композиционно использует переданный tx; автоматические join/savepoint не входят в этот план.
- Не использовать один tx параллельно из нескольких goroutine; не сохранять его в долгоживущих объектах и не использовать после завершения callback.
- Удалить неиспользуемое поле uow у transfer.Repository вместе с аргументом конструктора и соответствующим wiring. Не менять при этом границы транзакций.
- Оставить атомарность UpsertVerified внутри репозитория, пока нет конкретного сценария композиции с другими записями. При появлении такого сценария выделять вариант с явным tx; порядок остаётся: проверка WB → короткая DB-транзакция → commit → активация runtime.
- Не держать DB-транзакции во время WB HTTP, ожидания rate limiter, обработки Excel или других долгих вычислений. Сохранять существующие границы записи попытки перед отправкой и результата после отправки.
- Сохранить отдельный ограниченный контекст для rollback при отмене родителя и для уже предусмотренного сохранения результата внешней отправки.

### 2. Конфигурация подключения и бюджеты времени

- Сохранить pgxpool.ParseConfig; строить URI через net/url с корректным UserPassword и host/port либо явно заполнять поддерживаемые поля разобранной конфигурации. Не склеивать credentials с URI вручную.
- Сохранить совместимость существующих env-параметров. Проверить пароли со специальными символами, IPv6 и имена БД, требующие экранирования.
- Сделать TLS-режим явной частью конфигурации без скрытого отключения TLS; сохранить документированный сценарий локального запуска.
- Добавлять MaxConns, MinConns, MaxConnLifetime, MaxConnIdleTime и HealthCheckPeriod с валидацией и понятными значениями по умолчанию. Не увеличивать MaxConns без учёта числа экземпляров сервиса, воркеров и лимита PostgreSQL.
- Составить карту существующих deadline: обычный запрос, получение соединения, bulk UoW, сохранение результата публикации, rollback.
- Для обычных операций сохранить Config.Timeout. Для действительно долгих bulk UoW предусмотреть отдельный ограниченный бюджет на границе операции; caller cancellation и более ранний deadline сохраняются.
- Ожидание соединения входит в бюджет операции и измеряется отдельно от SQL. Не создавать транзакцию из короткого контекста, который будет отменён до завершения её callback.
- Удаление OperationContext из интерфейса pool допустимо только отдельным последующим шагом, когда все места использования получили эквивалентную явную политику времени.

### 3. Наблюдаемость

- QueryTracer: длительность SQL-операций, число ошибок и SQLSTATE; CopyFromTracer: длительность и количество скопированных строк.
- UoW: общая длительность, begin/commit/rollback, отмена и исход операции. Зафиксировать границы измерения, чтобы не складывать вложенные интервалы как независимые задержки.
- AcquireTracer и pool.Stat: ожидание соединений, занятые/свободные/всего, отменённые и ожидавшие получения соединения.
- Использовать существующий logger и, после определения способа экспорта, метрики. Одни записи zap не считать полноценным экспортом метрик.
- В логах — стабильное имя операции, длительность, исход и безопасные технические коды. Не логировать DSN, аргументы SQL, токены, содержимое payload и персональные данные; избегать сырого PgError.Detail.
- Для метрик использовать ограниченный набор labels. Не включать transfer_id, seller_id, полный SQL и произвольный текст ошибки.
- Добавить отдельный диагностический сценарий для lock wait и EXPLAIN (ANALYZE, BUFFERS); трассировка запроса сама по себе не объясняет источник ожидания.

### 4. Сканирование и декомпозиция

- Сначала разделить большие файлы внутри текущих пакетов без изменений SQL, порядка блокировок и интерфейсов: product_dispatch, product_attempt, product_reconciliation, product_abort; аналогично выделять связные операции media и batch.
- Не создавать новые сервисы, универсальный base repository или ORM только для уменьшения размера файлов.
- Пилот RowToStructByName провести в users на приватной структуре строки репозитория. SQL-теги и nullable-типы не переносить в доменные модели.
- Для каждого запроса задавать явный список колонок и однозначные aliases. Сохранить nullability, конвертацию ID/enum, размер digest, канонические хеши и Validate/ValidateIntegrity.
- QueryRow возвращает pgx.Row, а RowToStructByName требует CollectableRow. Для одиночного результата либо оставить Scan, либо осознанно перейти на Query с CollectOneRow/CollectExactlyOneRow в соответствии с текущим контрактом количества строк.
- Простые скалярные запросы оставить на Scan. Для больших результатов не заменять потоковую обработку неограниченным CollectRows; сохранять лимиты и пагинацию.
- Сравнить пилот по читаемости, allocations и времени обработки; расширять применение только при подтверждённой пользе. Структурное сканирование не заменяет проверки данных.
- Общий ReserveIDs выделять при реальном повторном использовании. Сохранять параметризованный regclass, проверку count/количества результатов и явный tx. Пропуски sequence после rollback допустимы; алгоритм не должен требовать непрерывности ID.
- Перенос telegramview в Telegram storage выполнять лишь как отдельную организационную задачу после проверки направления импортов. Сам путь файла не доказывает нарушение слоя.

### 5. Ошибки и повторы

- Общий pgerr предоставляет техническую классификацию и сохраняет исходный PgError через unwrap/errors.As.
- Классифицировать 23505 (unique_violation), 23503 (foreign_key_violation), 23514 (check_violation), 40001 (serialization_failure), 40P01 (deadlock_detected), 55000 (object_not_in_prerequisite_state).
- Проект явно использует 55000 для защиты иммутабельности; не называть любой 55000 универсальным TriggerException и не менять коды существующих триггеров ради рефакторинга.
- Интерпретация ConstraintName остаётся в фиче: конфликт имени кабинета, повторный продавец, нарушение идемпотентности и внутренняя ошибка — разные ситуации.
- Сохранять существующие контракты pgx.ErrNoRows, core_errors и errors.Is(context.Canceled/DeadlineExceeded). Не преобразовывать любой FK/CHECK в ошибку пользовательского ввода.
- Внедрение pgerr не включает автоматические повторы. Повтор DB-транзакции — отдельная задача для конкретной операции после проверки всех побочных эффектов.
- Если такой повтор нужен для 40001/40P01: повторять весь DB callback с новым tx, ограничением попыток/времени и backoff; исключить WB-мутации и другие неповторяемые внешние эффекты.
- Ошибка транспорта при commit может оставлять результат неизвестным. Не считать её доказанным rollback и не повторять автоматически всю бизнес-операцию; использовать существующие ключи идемпотентности и чтение сохранённого состояния.

## Схема и производительность

### 1. Миграции user ID

- Расширять согласованно users.id, author_user_id в card_import_sessions и связанную serial sequence до bigint; проверить все зависимости по каталогу БД, а не только по списку известных таблиц.
- Сохранить значения, PK/FK, ON DELETE SET NULL, default nextval, владение последовательностью, её текущее состояние и корректные bounds.
- Для существующей БД выпускать новую миграцию со следующим свободным номером. Не переписывать применённые baseline migrations и не пересоздавать таблицы с данными ради группировки файлов.
- Перед реализацией оценить блокировки ALTER TABLE, объём переписывания данных/индексов и зависимости views. Выбрать короткое окно обслуживания либо отдельный поэтапный переход для большого объёма данных.
- Проверить fresh install и upgrade с данными, включая создание и ссылки на ID за пределами int4.
- Downgrade к int4 не является безусловно безопасным. Он должен проверять значения и состояние sequence и явно отказывать, если диапазон int4 уже превышен.

### 2. Индекс очереди

- Зафиксировать текущий запрос ListPendingPreparationGroups и его keyset/ORDER BY. Сравнить планы существующего UNIQUE и нового partial index на разных долях завершённых групп и размерах transfer.
- Кандидат: (transfer_id, source_group_id, target_id) INCLUDE (id) WHERE preparation_status = 'running' AND preparation_result_revision = 0.
- Кандидат — гипотеза до EXPLAIN (ANALYZE, BUFFERS) и замеров задержки. INCLUDE покрывает поля group_target, но не устраняет join с transfer_targets и не гарантирует index-only scan.
- Оценить размер индекса, стоимость записи и изменение участия строк в partial index при смене статуса. Не удалять UNIQUE и другие индексы, обслуживающие ограничения целостности.
- Старый узкий partial index удалять только после проверки всех его потребителей. Для большой рабочей таблицы отдельно определить необходимость CREATE INDEX CONCURRENTLY и совместимость с транзакционной моделью мигратора.

### 3. Блокировки и агрегация

- Измерить время удержания блокировки transfers, ожидание разных групп одного transfer и стоимость outcome aggregation.
- Первые меры: сократить работу внутри UoW, исключить внешние ожидания, улучшить подтверждённые планы запросов, сохранить единый порядок блокировок.
- Повышение числа соединений не устраняет сериализацию на одной строке. Не увеличивать конкурентность вслепую.
- Снятие общей блокировки, инкрементальные счётчики и отдельный reducer требуют самостоятельного проектирования: защита от повторного учёта replay, атомарность переходов и восстановление после сбоя. Они не входят в механическое разбиение файлов.

## Порядок внедрения и критерии завершения

### Фаза 0. Контракты и исходные измерения
- Подготовить изолированную PostgreSQL 18 для интеграционных тестов через testcontainers-go либо существующий воспроизводимый контейнерный запуск.
- Интеграционные тесты не должны подключаться к рабочей БД по умолчанию. В обязательном DB-задании CI недоступность PostgreSQL — ошибка, не тихий Skip.
- До смены инфраструктуры покрыть: совместный rollback артефакта и проекции; ошибку между связанными записями; panic/cancel; ошибку commit; одинаковый и конфликтующий replay; конкурентные результаты одной и разных групп; immutability.
- Для неопределённого commit проверить отсутствие автоматической повторной отправки WB и корректность восстановления по сохранённому состоянию.
- Снять воспроизводимый baseline: query count, latency/p95, allocations выбранного mapper, CopyFrom throughput, ожидание соединений и блокировок. Численные критерии регрессии фиксировать по этому baseline до оптимизаций.
- Готовность: проверки реально выполняются на изолированной БД; результаты измерений воспроизводимы; выявленные сбои разобраны до дальнейших изменений.

- Готовность: контракты данных сохранены, бинарник и тесты компилируются и проходят.

### Фаза 4. Базовые миграции и измеренный индекс [ВЫПОЛНЕНО ДЛЯ ЧИСТОЙ БД]
- `wb.users.id` создаётся как `BIGSERIAL` в `000001_users`; обе ссылки `author_user_id` создаются как `BIGINT` в `000003_card_import`.
- Покрывающий частичный индекс `transfer_group_targets_pending_keyset_idx` создаётся сразу в `000004_transfer`. Ранее измеренный EXPLAIN для этого индекса показывал переход на Index Only Scan и уменьшение времени запроса с 0.835 до 0.535 мс; замеры не являются гарантией для других данных.
- Отдельные переходные миграции 8/9 и их откаты удалены, потому что пользователь переинициализирует БД. Актуальна только последовательность 1–7 для установки с пустой БД. Последовательность 1–7 фактически применена к новой изолированной PostgreSQL 18 через `make postgres-integration-test-local`; затем прошли все cardimport и transfer PostgreSQL-интеграционные тесты. Это подтверждает свежую установку и проверенные сценарии, но не заменяет отдельные нагрузочные измерения.

### Фаза 5. Отдельные изменения конкурентности при необходимости
- Начинать только если измерения подтвердили существенную конкуренцию за строку transfers или дорогую агрегацию.
- Подготовить отдельный протокол согласованности и тесты сбоев/повторов; затем сравнить с baseline.
- Готовность: ускорение подтверждено, атомарность/идемпотентность/переходы состояния сохранены. При отсутствии проблемы фазу не выполнять.

## Правила выполнения

- Один шаг не должен одновременно менять маппинг, схему, транзакционные границы и бизнес-поведение.
- Общий критерий для текущей переинициализации: сохранение инвариантов, успешная установка схемы с пустой БД и отсутствие необъяснённой регрессии по измеренным показателям.
- Запускать проверки, соответствующие изменению; тесты на поведение важнее проверок механического расположения кода.
- Все новые/изменённые комментарии в коде — по-русски.
- После реализации каждого шага синхронизировать Serena: факты о внедрённом коде записывать в профильные памяти, не смешивать их с ещё не реализованными решениями этого плана.
