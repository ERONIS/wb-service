# Wildberries Core Client (`internal/core/transport/wb`)

## Architecture & Responsibilities
- Single process-wide `Clientset` manages per-seller credential-bound executors for WB API operations. Content is the only currently registered API catalog; unused Prices and General operations were removed.
- Package layout follows client-go style; features select only the Content operations they need in their own `transport/wb` adapters:
  - Direct domain binding: `SellerID` and `ClientGeneration` come directly from `internal/core/domain/wb_identity.go`. `credentials.go` deleted entirely.
  - `clientset.go`: `NewClientset(ctx, logger, bucketSpecs)` is the sole constructor: the composition root supplies API bucket specs, while it creates a 45s default HTTP client, builds the rate limiter registry, and acquires shared transport from `http.DefaultTransport`. Each operation owns a lowercase, validated Wildberries API subdomain; request preparation combines that host with the operation path under HTTPS per call. Regression tests cover host validation and URL routing for both Content and a synthetic Common operation. `Clientset` stores no API-specific host. `options.go`, `ClientOptions`, and envconfig were deleted entirely. `NewCandidate(id, name, token)` checks seller ID and nonempty name, delegates token shape validation to `credentials`, and builds credentials for dynamic activation (`ActivateCandidate`, `RemoveCabinet`); the generic executor is built directly. Candidates expose value fields `ID` and `Name` plus `Generation()` and generic `Executor()`; the wbcabinet verifier passes a Content ping operation to this executor. `Cabinets()` returns sorted value copies of active `CredentialCandidate` entries, replacing the metadata-only `CabinetInfo`; these copies also expose `Executor()`. The registry shares a connection pool, uses a value `sync.RWMutex` for cabinet access, and re-exports `SellerID` and `ClientGeneration` for transport-level callers.
  - `Clientset` stores one API-neutral `client.Executor` directly in each immutable candidate; there is no `CabinetClient` wrapper. The validated cabinet token is stored in its `APIClient` and added to every fresh HTTP request in `doAttempt`; flow control is bound when the executor is constructed.
  - `flowcontrol/`: Token bucket rate limiting, rate admission, header observation (`X-Ratelimit-*`).
  - `policy/`: Safe retry mode and fixed default of three read attempts. `flowcontrol/` owns the 500 ms base backoff delay and limiter admission.
  - `transport/`: Shared HTTP connection pool and HTTP/1.1 configuration; `SharedTransport.NewHTTPClient` clones the base `http.Client`, attaches the shared transport, and denies redirects. Clientset no longer handles a RoundTripper directly. The Authorization RoundTripper, generic `Chain`, and wrapper factories are removed. `client.doAttempt` attaches `httptrace.ClientTrace` directly to each attempt context; `WroteRequest` counts actual dispatches for delivery classification (`NotDispatched` versus `UnknownDelivery`) and request logging.

## Cabinet Lifecycle & Dynamic Loading
- Static cabinet env parsing is removed.
- At application startup, `internal/feature/wbcabinet.Initialize(ctx)` calls `service.Restore(ctx)` to load active cabinets from PostgreSQL (`wb.api_cabinets`) and dynamically register them into `Clientset`.
- A transient `/ping` verification failure leaves the cabinet active in PostgreSQL but absent from `Clientset`; the background restore worker retries pending cabinets every 30 seconds. Until activation succeeds, database-derived publication targets can reach the error-feed poller and fail with `get WB cabinet executor: WB cabinet: not found`. The feed uses `errgroup.WithContext`, so one such failure can cancel concurrent cabinet queries and surface additional `context canceled` SQL/transport warnings. Verification currently wraps all prepare errors with `ErrVerification` (`unauthorized`), including transient transport failures; inspect the nested cause before diagnosing token rejection.
- New cabinets at runtime are added exclusively via Telegram (`feature/wbcabinet`) or initial database seed (`scripts/bootstrap_cabinets.sql`).

## Operational Rules
- **Core Retry Policy**: Automatic retries depend on `OperationKindRead` plus `RetryModeReadSafe`, not HTTP method. Content operation specs use local `safeGetJSON`, `safePostJSON`, and independent `mutationPostJSON` constructors for common shapes; ping remains an explicit no-retry read, and multipart upload remains explicit. Dynamic subject paths still validate IDs before constructing an operation. Catalog/error-list reads use POST and can retry. Mutation operations use `RetryModeNever` in the core executor. Publication sends each media link/file mutation once per business attempt; only external media downloads use its local retry loop. Ambiguous mutation outcomes are classified for reconciliation rather than automatically resent.
- **Rate Admission**: Calls pass through `flowcontrol` token buckets before hitting network.
- **Bounded Reading**: Response reading is strictly bounded by size limits to prevent memory exhaustion from oversized WB payloads.
- **Unified Logging**: Exactly one structured Zap log entry per logical request capturing attempt count, status, latency, and delivery state.

## Registry Consistency
- Clientset stores a single immutable candidate value per cabinet. The executor accessor returns the executor from that entry together with the lookup error. Pinned lookup checks generation and retrieves the executor from the same entry under one read lock; token rotation cannot substitute a different generation between these steps. A mismatch returns `ErrClientGenerationChanged` (core conflict). Already acquired executors remain usable; removal does not cancel in-flight calls.

## Catalog Traversal
- `wb/api/content/v1/catalog` owns active/trash pagination, cursor-cycle detection, nmID deduplication, cancellation, and bounded page counts. `ErrPageLimit` means an incomplete search, never proven absence. `FindByVendorCode` performs exact matching over the complete search result and preserves multiple distinct matches.

## Integration Boundaries
- Composition root passes Content bucket specs to `Clientset` and the shared registry to feature-owned WB adapters. `cardprepare/transport/wb` calls only category, attribute and directory Content operations; `cardpublication/transport/wb` calls only catalog, error-feed and pinned mutation operations, including multipart encoding; `statistics/transport/wb` calls only CardsList. `wbcabinet/transport/wb` verifies candidates with Content ping. Core owns operation specs, executor selection, pinned-generation checks, rate limits and HTTP safety. Publication also uses a separate MediaDownloader.
- `wb/credentials.ValidateTokenShape` owns token size/whitespace/three-part checks and is reused by `ParseToken` and `Clientset.NewCandidate`; `ParseToken` owns canonical seller claim normalization, expiry and permission-bit decoding. Cabinet name length (128 runes) belongs to `wbcabinet/service`, not `Clientset`. `client.NewAPIClient` takes no retry settings; it uses the fixed `policy` attempt count and `flowcontrol` base delay. The Prices permission bit remains decoded and displayed for cabinet information even though no Prices API requests are made. Parsing does not verify authenticity; wbcabinet verifies the exact token via Content `/ping`. Invalid and expired token errors are distinct sentinels wrapping core invalid-argument. Cabinet ownership, persistence and activation remain in the feature.
- `SellerID` is the normalized raw UUID from token `sid` and identifies the seller and its single cabinet; `ClientGeneration` fingerprints the exact token. Generation checks do not establish seller ownership or publication authorization.
- Feature-specific catalog observations, reconciliation decisions, and publication outcomes remain business concerns. Media downloading in publication is a separate unauthenticated HTTP client, outside WB API rate limiting.

## Regression Checks
- Transport unit tests previously located in `api/content/v1/operations_test.go`, `api/content/v1/catalog/cards_test.go`, and `credentials/token_test.go` were pruned. Focused `client/execute_test.go` coverage checks per-client Authorization headers over a shared HTTP transport, plus `NotDispatched` versus `UnknownDelivery` when an HTTP attempt fails before or after `WroteRequest`; broader integration coverage remains in feature layers (`cardpublication`, `transfer`, `wbcabinet`). No live WB access is needed.
