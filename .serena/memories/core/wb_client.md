# Wildberries Core Client (`internal/core/transport/wb`)

## Architecture & Responsibilities
- Single process-wide `Clientset` manages per-seller credential-bound executors for WB API operations. Content is the only currently registered API catalog; unused Prices and General operations were removed.
- Package layout follows client-go style; features select only the Content operations they need in their own `transport/wb` adapters:
  - Direct domain binding: `SellerID` and `ClientGeneration` come directly from `internal/core/domain/wb_identity.go`. `credentials.go` deleted entirely.
  - `clientset.go`: `NewClientset(ctx, logger, bucketCatalog)` is the sole constructor: the composition root supplies the validated Content API bucket catalog, while it builds the rate limiter registry and creates one 45s HTTP client attached to shared transport cloned from `http.DefaultTransport`; all cabinet executors use that same client pointer. The client is constructed once during `NewClientset`; `NewCandidate` only creates a cabinet executor. Each operation owns a lowercase, validated Wildberries API subdomain; request preparation combines that host with the operation path under HTTPS per call. `Clientset` stores no API-specific host. `options.go`, `ClientOptions`, and envconfig were deleted entirely. `NewCandidate(id, name, token)` checks seller ID and nonempty name, delegates token shape validation to `credentials`, and builds credentials for dynamic activation (`ActivateCandidate`, `RemoveCabinet`); the generic executor is built directly. Candidates expose value fields `ID` and `Name` plus `Generation()` and `Executor()` returning `*client.APIClient`; the wbcabinet verifier passes a Content ping operation to that client. `Cabinets()` returns sorted value copies of active `CredentialCandidate` entries, replacing the metadata-only `CabinetInfo`; these copies also expose `Executor()`. The registry shares a connection pool, uses a value `sync.RWMutex` for cabinet access, and uses `domain.SellerID` and `domain.ClientGeneration` directly in candidate, registry, and execution signatures; package-local aliases are removed. `clientset.go` keeps public construction, registration, lookup, and cleanup methods above candidate accessors and private lookup/validation helpers; this ordering does not change runtime behavior.
  - `Clientset` stores one `*client.APIClient` directly in each immutable candidate; the former `client.Executor` interface is removed. `client.ExecuteResponse`, `Clientset` accessors, and WB registry interfaces use the concrete pointer; there is no `CabinetClient` wrapper. The validated cabinet token is stored in its `APIClient` and added to every fresh HTTP request in `doAttempt`; flow control is bound when the executor is constructed. In `client/execute.go`, `ExecuteResponse` supplies typed results above `APIClient.Execute`; the latter orchestrates preparation, the complete logical request, response decoding and final logging. `client/retry.go` owns the loop over allowed attempts, limiter waits, per-attempt deadlines and retry delay/classification. `client/attempt.go` owns one HTTP dispatch, response reading, status classification and delivery evidence. `requestTrace` groups stable request details and accumulated attempt metrics; its final log receives `executionResult` and the returned error directly, without copying outcome fields into trace state. The emitted log fields and severity rules remain unchanged. `errors.go` holds classified delivery-aware errors. The former one-function `execute_response.go` file is removed.
  - `flowcontrol/`: Token bucket rate limiting, rate admission, header observation (`X-Ratelimit-*`).
  - `policy/`: Validated operation definitions and success statuses, safe retry mode, three read attempts, and the 500 ms retry base delay. Retry mode and success-status helpers are colocated in `retry.go`. `policy/` owns bucket specifications and their validation, while `flowcontrol/` owns limiter admission and rate-header observation; its named sentinel errors live together in the same-package file `flowcontrol/errors.go` (including the queue-full error that wraps core `ErrQueueFull`), while response-header parse errors with input-specific details stay at the parsing site; `client` performs retry waits.
  - `transport/`: Shared HTTP connection pool with HTTP/2 negotiation and HTTP/1.1 fallback; its cloned `http.Transport` enables HTTP/2 attempts and clears the former HTTP/1.1-only TLSNextProto override, leaving ALPN selection to Go; `SharedTransport.NewHTTPClient(timeout)` constructs the one client with a fixed timeout, shared transport, and redirects denied; `Clientset.NewCandidate` passes its shared client pointer to `client.NewAPIClient`, which retains that pointer without copying. Cabinet tokens stay on their executors and are attached per HTTP request. Clientset no longer handles a RoundTripper directly. The Authorization RoundTripper, generic `Chain`, and wrapper factories are removed. `client.doAttempt` attaches `httptrace.ClientTrace` directly to each attempt context; `WroteRequest` counts actual dispatches for delivery classification (`NotDispatched` versus `UnknownDelivery`) and request logging.

## Cabinet Lifecycle & Dynamic Loading
- Static cabinet env parsing is removed.
- At application startup, `internal/feature/wbcabinet.Initialize(ctx)` calls `service.Restore(ctx)` to load active cabinets from PostgreSQL (`wb.api_cabinets`) and dynamically register them into `Clientset`.
- A transient `/ping` verification failure leaves the cabinet active in PostgreSQL but absent from `Clientset`; the background restore worker retries pending cabinets every 30 seconds. Until activation succeeds, database-derived publication targets can reach the error-feed poller and fail with `get WB cabinet executor: WB cabinet: not found`. The feed uses `errgroup.WithContext`, so one such failure can cancel concurrent cabinet queries and surface additional `context canceled` SQL/transport warnings. Verification classifies HTTP 401/403 as token rejection, HTTP 429 as rate limited, HTTP 5xx and transport/response failures (including invalid ping payloads) as transient. The service preserves that category instead of adding `ErrVerification` to every preparation failure; transient restoration failures remain pending for retry.
- New cabinets at runtime are added exclusively via Telegram (`feature/wbcabinet`) or initial database seed (`scripts/bootstrap_cabinets.sql`).

## Operational Rules
- **Core Retry Policy**: Automatic retries depend on `OperationKindRead` plus `RetryModeReadSafe`, not HTTP method. `policy.NewOperation` guarantees that read-safe retry mode belongs only to read operations. `attemptLimit` therefore uses only the validated retry mode to choose one or three attempts; `shouldRetry` then checks only remaining attempts, live context, and retryability of the result. Content operation specs use local `safeGetJSON`, `safePostJSON`, and independent `mutationPostJSON` constructors for common shapes; ping remains an explicit no-retry read, and multipart upload remains explicit. Dynamic subject paths still validate IDs before constructing an operation. Catalog/error-list reads use POST and can retry. Mutation operations use `RetryModeNever` in the core executor. Publication sends each media link/file mutation once per business attempt; only external media downloads use its local retry loop. Ambiguous mutation outcomes are classified for reconciliation rather than automatically resent.
- **Transport Retry Classification**: The executor considers a transport/read error retryable only for `io.EOF`, `io.ErrUnexpectedEOF`, or a `net.Error` timeout; explicit context cancellation is excluded. Per-attempt deadline errors are covered by the same timeout check, while the overall context and read-safe operation policy still gate retries. OS-specific closed/reset/pipe errors are no longer separately allowlisted. Response-layer transport-error and HTTP-status retry predicates are colocated in `client/response/retry.go`; the executor still makes the final retry decision from the operation's read-safe policy and live context.
- **Rate Admission**: Calls pass through `flowcontrol` token buckets before hitting network. `policy` owns the operation's `BucketID`, `BucketSpec` (interval, burst, waiter capacity), and validation of the complete bucket catalog; `flowcontrol` owns runtime limiter state. Content bucket literals use `contentBucket(id, interval, burst)` with a shared waiter limit. `api/content/v1` builds its `policy.BucketCatalog` at package initialization via `policy.NewBucketCatalog`, which checks nonempty specs, each bucket's ID/interval/burst/waiter capacity, and duplicate IDs, then stores a private map. `BucketCatalog()` returns this validated immutable catalog. `flowcontrol.NewRegistry` accepts the catalog directly without revalidating or rebuilding the spec map; private `bucketLimiter` instances trust its specs. The limiter wait/observation methods are private and assume a registry-provided nonnil limiter; `Registry.Wait` checks the incoming context. Static operation specs remain checked by `policy.NewOperation`; dynamic Content factories retain their own input checks, while rate-header parsing remains a runtime check of WB responses.
- **Flowcontrol Reservation Invariants**: Validated `BucketSpec` guarantees positive burst. `bucketLimiter` reserves one token per request or a clamped amount no greater than burst when reconciling server headers, so `rate.Reservation.OK()` failure is unreachable; its reservation and observation helpers no longer return synthetic reservation errors. A delayed reservation is still canceled under the limiter mutex when context ends. `Registry.Observe` still reports malformed header parse errors and applies the local 429 cooldown even when parsing fails. In the slow path, `wait` defers releasing the admission marker before the waiter slot; both releases run synchronously on return, including cancellation.
- **Bounded Reading**: Response reading is strictly bounded by size limits to prevent memory exhaustion from oversized WB payloads.
- **Query Encoding**: Request query structs use `url` tags with a nonempty parameter name and at most one `omitempty` option; unsupported or repeated options are rejected. The generic encoder accepts string and signed-integer fields, then uses `url.Values.Encode` for the URL query string.
- **Prepared Request Body**: `request.Prepare` relies on `policy.NewOperation` for the nonempty operation ID, validates the operation's body mode, serializes its body, and enforces the operation's request size limit once for every format. A zero-value operation is still rejected by the unsupported body-mode fallback. `prepareBody` selects no-body, JSON, or multipart encoding; `prepareMultipartBody` owns one-file multipart form creation, file writing, writer closure, and the matching boundary-bearing content type. `Prepared` retains serialized `bodyBytes`, with nil meaning no request body and nonnil meaning a body is present; it does not retain the body mode. Each `Prepared.NewHTTPRequest` call creates a fresh `bytes.Reader` from nonnil bytes so retry attempts get independent request bodies. Only `Prepare` constructs populated `Prepared` values in the application; the executor checks the incoming context and operation before invoking `NewHTTPRequest`.
- **Unified Logging**: Exactly one structured Zap log entry per logical request capturing attempt count, status, latency, and delivery state. A malformed rate-limit observation now logs its first actual cause in `rate_limit_observation_error` (plus count) and raises the completion log to Warn even on an otherwise successful request. A classified `context_canceled` error without observation error logs at Debug. Non-2xx JSON response bodies are read within the operation limit, and `response.ErrorSummary` contributes only bounded, control-character-sanitized allowlisted WB fields (`code`, `title`, `errorText`, `requestId`) to the classified error message; a numeric `code` is supported, and malformed or unexpected field types are ignored. Raw bodies are never logged. The trace stores HTTP status codes directly in an `[]int`; its length is the attempt count, and the same slice is logged as `attempt_statuses`. The trace is always allocated by `Execute`, including invalid-client calls (which skip logging without a logger).
- **Executor Error and Response Handling**: Transport causes use a private safe-display wrapper with `Unwrap`, so `errors.Is`/`errors.As` still reach the original cause without printing a URL or query in `Error()`. Interrupted-retry causes use `%w`/`errors.Join` and preserve unwrapping. A nil response with nil error is ruled out by `http.Client.Do`; the executor handles nonnil response plus error from redirect checks. Validated operations have only JSON or no-body response modes, so JSON bodies are read with a limit and no-body responses are closed.
- **Read Retry Backoff**: `policy.DefaultRetryBaseDelay` fixes a 500 ms initial read-retry delay; the private `client.waitRetry(ctx, retryNumber, retryAfter)` applies exponential backoff, honors a longer Retry-After, and stops on context cancellation. It is called only after `shouldRetry` has admitted a retry, so retry numbers and contexts are already valid. `flowcontrol` owns only rate admission and response rate-limit observation; its former backoff function is removed.

## Error Boundary Invariants
- Core error codes, delivery evidence, safe diagnostics, retries, and feature boundaries are documented in `mem:core/wb_errors`.
- Keep `client.ClassifiedError` compatible with the external media downloader and publication classifiers; persistently stored publication codes require a classifier version when their meaning changes.

## Registry Consistency
- Clientset stores a single immutable candidate value per cabinet. The executor accessor returns the executor from that entry together with the lookup error. Pinned lookup checks generation and retrieves the executor from the same entry under one read lock; token rotation cannot substitute a different generation between these steps. A mismatch returns `ErrClientGenerationChanged` (core conflict). Already acquired executors remain usable; removal does not cancel in-flight calls.

## Content API Catalog
- `api/content/v1` keeps only operations used by current WB adapters; unused parent categories, tags-list, and cards-update endpoints and their dedicated DTOs, size limits, and cards-update bucket have been removed. `CardTag` remains part of the active card DTO.
- Responses with WB's common `data` field plus `ResponseMeta` use `DataResponse[T]`; endpoint-specific response names are aliases with concrete `T`, preserving their JSON shape and caller access to `Data` and embedded metadata. Locale-only query names alias `LocaleQuery`. Catalog operation IDs are literals next to their specs; validated private operations are still returned through getters.

## Catalog Traversal
- `wb/api/content/v1/catalog` owns active/trash pagination, cursor-cycle detection, nmID deduplication, cancellation, and bounded page counts. `ErrPageLimit` means an incomplete search, never proven absence. `FindByVendorCode` performs exact matching over the complete search result and preserves multiple distinct matches.

## Integration Boundaries
- Composition root passes the validated Content bucket catalog to `Clientset` and the shared registry to feature-owned WB adapters. `cardprepare/transport/wb` calls only category, attribute and directory Content operations; `cardpublication/transport/wb` calls only catalog, error-feed and pinned mutation operations, including multipart encoding; `statistics/transport/wb` calls only CardsList. `wbcabinet/transport/wb` verifies candidates with Content ping. Core owns operation specs, executor selection, pinned-generation checks, rate limits and HTTP safety. Publication also uses a separate MediaDownloader.
- `wb/credentials.ValidateTokenShape` owns token size/whitespace/three-part checks and is reused by `ParseToken` and `Clientset.NewCandidate`; `ParseToken` owns canonical seller claim normalization, expiry and permission-bit decoding. Cabinet name length (128 runes) belongs to `wbcabinet/service`, not `Clientset`. `client.NewAPIClient` takes no retry settings; it uses the fixed `policy` attempt count and base delay. The Prices permission bit remains decoded and displayed for cabinet information even though no Prices API requests are made. Parsing does not verify authenticity; wbcabinet verifies the exact token via Content `/ping`. Invalid and expired token errors are distinct sentinels wrapping core invalid-argument. Cabinet ownership, persistence and activation remain in the feature.
- `SellerID` is the normalized raw UUID from token `sid` and identifies the seller and its single cabinet; `ClientGeneration` fingerprints the exact token. Generation checks do not establish seller ownership or publication authorization.
- Feature-specific catalog observations, reconciliation decisions, and publication outcomes remain business concerns. Media downloading in publication is a separate unauthenticated HTTP client, outside WB API rate limiting.

## Regression Checks
- No direct WB Core transport unit tests are currently present. External WB access is not needed to exercise the executor with an in-memory HTTP transport when tests are added.
